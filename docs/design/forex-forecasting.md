# Forex forecasting, as built (P13-T05)

How P13-T05 was built: the forecasting framework, its evaluation and the forecast API. The design is in [forex-technical-design.md](forex-technical-design.md) section 7, and the v1 model scope in DEC-22. The evidence is [reports/quality/qg-15-forex-model-validation.md](../../reports/quality/qg-15-forex-model-validation.md), generated by `scripts/forex_model_report.py`.

**Honesty rules, all enforced in code and tests:**
- **Baselines.** Every model is compared with the no-change, random-walk and drift baselines, and the comparison is reported even when a baseline wins.
- **No demonstrated edge.** When no model beats every baseline significantly, the **random-walk baseline is published** and is labelled "no demonstrated edge".
- **Calibration label.** A probability is "Requires calibration" until held-out calibration passes, and is never called a success rate.
- **Simulated data.** Any result on simulated data says so: "on simulated data: not evidence about real markets".
- **No future data.** No future data reaches a feature, a label or a model (leakage audit).
- **No language model** computes or edits a forecast.

## 1. Code

The code is in `backend/app/modules/forex/forecast/`:

| File | Content |
|---|---|
| `features.py` | 12 point-in-time features: past returns over 1 to 10 bars, realised volatility over 10 and 30 bars, RSI(14), MACD histogram, Bollinger %b, ATR ratio and the event-risk window. Labels are forward log returns. Also the feature-set and data-snapshot hashes |
| `models.py` | The baselines; ARIMA (SARIMAX with one Kalman pass and the exact ARMA cumulative variance); Random Forest, LightGBM and XGBoost (a direction classifier and a mean regressor, with residual quantiles from the calibration window); the ensemble; EWMA and HAR volatility |
| `evaluation.py` | Purged expanding walk-forward folds, metrics, the Diebold–Mariano edge test, and the leakage audit |
| `calibration.py` | Reliability bins, ECE, isotonic or Platt recalibration, and the calibration status |
| `drift.py` | PSI and KS per feature, error drift against the random walk, and the breach rules |
| `pipeline.py` | One training run for a pair and horizon, and what gets published |
| `store.py` | `forex_model_versions` (the registry) and `forex_forecasts` (append-only), migration 0022, and retraining approval |
| `service.py` | Training from stored candles, with event-risk windows from the calendar |
| `api.py` | The forecast and evaluation endpoints |

A run needs at least 400 usable bars, otherwise nothing is published ("not enough history"). It uses the most recent 2,000 bars (`forex_forecast_max_bars`).

## 3. Evaluation (design section 7.3)

- **Splits.**
  - Expanding walk-forward: the first half of the usable bars is history, then test windows of one-eighth each.
  - In every fold the fit window, the calibration window (the last 20% of history) and the test window are separated by purge gaps of h bars, so no training label reaches the next window. This is checked on every fold.
- **Metrics,** on out-of-sample test bars only:
  - direction accuracy, log loss, Brier score and pinball loss;
  - CRPS (approximated as twice the mean pinball loss over 5 quantiles);
  - 50% and 80% interval coverage;
  - RMSE and MAE of the mean return.
- **Edge.** A model has a demonstrated edge only if its log loss is lower than every baseline's and a Diebold–Mariano test (Newey–West variance with h − 1 lags) gives p < 0.05 against each.
- **Calibration.**
  - Each fold recalibrates the probability on its own calibration window (isotonic with 300 or more rows, otherwise Platt).
  - Recalibration is used only when it lowers the out-of-sample log loss: small windows otherwise just learn their own base rate. The probability actually reported and published is recorded as `raw` or `recalibrated`.
  - The status is `calibrated` only with at least 300 held-out bars, ECE ≤ 0.05, and no bin of 20 or more bars off by more than 0.10.
- **Leakage audit.** For test origins, everything unknown at prediction time is replaced with noise; the prediction must not change. Every model passes. Two deliberately leaky models fail: one reads the label, one reads the next bar's return.
- **Drift.**
  - PSI and KS are reported for every feature.
  - A breach needs one of: PSI > 0.25 on at least half the features, PSI > 2 on any one feature, or a recent log loss worse than the random walk's by more than 0.02.
  - Single-feature drift is reported, not acted on: persistent rolling features make a short-window PSI noisy.
  - A breach disables the pair and horizon. The job then skips it until `store.approve_retraining` records an approval.
- **Reproducibility.** Every version records the model and its parameters, the feature-set hash, the data-snapshot hash, the code version (`GIT_SHA` or `fx-forecast-1`) and the seed (7). Runs on the same data give the same version.

## 4. What a forecast contains (design section 7.2)

`GET /api/v1/forex/forecasts?instrument=&horizon=` returns `available` or `unavailable` with the reason (no history, or drift).

**Forecast fields:**
- **Time:** `as_of` (the last closed bar), `generated_at`, the true `age_seconds` and `fresh`.
- **Probabilities:** `prob_up` and `prob_down`, with `probability_label` ("Requires calibration" or "Calibrated") and the note "A model probability, not a success rate".
- **Ranges:** the return quantiles q10–q90; the median price and the 50% and 80% price intervals (last close × exp(quantile), in `Decimal` at the pair's display precision); `expected_volatility` from EWMA or HAR, whichever scored better.
- **Data:** the data types used (for example `simulated`).

**The model:** name, family, version, hashes, code version, seed, edge, statement, data types, probability source, calibration status and drift status.

**The out-of-sample record:** the published model's metrics next to each baseline's.

`GET /api/v1/forex/forecasts/evaluation` returns every model and baseline, whatever the outcome, with the volatility scores and the drift report.

Both endpoints need sign-in and the forex flag.

## 5. Running

- **Job:** the worker job `forex_forecast_train` runs hourly at :20 when forex is switched on, for every active pair and each horizon in `forex_forecast_horizons`. Each run is idempotent per hour.
- **Run time:** a run takes about 5 to 10 seconds for 1,500 bars.
- **Data in development:** only the simulated feed exists, so only the short horizons gather enough history.

## 6. Dependencies (DEC-22)

numpy, scipy, scikit-learn, statsmodels, LightGBM and XGBoost (CPU build), plus their dependencies (pandas, patsy, joblib and others). All are BSD, MIT, Apache-2.0 or Zlib licensed, checked on 2026-10-14, and pip-audit reports no known vulnerabilities. Models compute in `float64`. Prices shown to users are converted to `Decimal` at the boundary. Money, pips, lots and position sizes never pass through this module.
